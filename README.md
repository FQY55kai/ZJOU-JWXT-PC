# ZJOU 教务系统 PC 移植

把一台 **x86-64 主机独占大作**搬到 Windows 上原生运行。不走模拟器，不走"运行时翻译二进制"（HLE），走**静态重编译**：离线把主机镜像里的机器码翻成可编译的 C++，再配上我们自己写的运行时与渲染器。

> **本仓库不含任何游戏数据、不含反编译产物。** 只含工具与文档；使用者需自备正版。

---

## 一、为什么重新开一个项目

上一个仓库（运行时翻译路线）已经能跑：能进世界、能操作、画面正常。它的账本是这样的（世界场景稳态，实测）：

| 环节 | 每帧 | 主机上对应 |
|---|---|---|
| 帧总长 | **200.7 ms**（5.0 fps） | 33.3 ms（30 fps） |
| 命令录制 | **149.1 ms**，35,766 次调用，6 线程 | ≈0，硬件直接消费绘制包 |
| GPU 执行 | 103.3 ms | ≈33 ms |
| 主机内存 → 宿主副本 | 45.9 ms / 122.9 MB | 0，统一内存 |
| 宿主副本 → 主机内存 | 40.9 ms / 42.5 MB | 0 |
| 描述符翻译 | 每帧 11,224 张表 | 0，shader 直接按地址读 |

这五项**没有一项是"实现得不够好"**，全是"主机省掉的那一层，我们必须自己做一遍"。两天的调参实测：能拿回 10–20%，拿不回 6 倍。所以换路线。

## 二、这条路能买到什么（以及买不到什么）

先说清楚最容易搞错的地方：**guest 和 host 都是 x86-64，这里没有"翻译红利"**。N64Recomp / XenonRecomp / PS2Recomp 挣的是跨 ISA 的钱（MIPS/PPC 每条指令在 PC 上都要解释一次）；本作 guest ISA 与 host 相同，机器码本来就是原生的。

静态重编译在这里买到的是另外三样：

| 买到 | 为什么值钱 | 对应上面的成本 |
|---|---|---|
| **可编辑的代码** | 现在写死在二进制里的调用序列，变成可改的 C++：可以把 4,544 条绘制合成批量提交 | 命令录制 149 ms |
| **图形边界整体替换** | 不再"翻译主机图形调用"，而是在提交边界写自己的渲染器（bindless + GPU-driven），像 RT64 那样 | 描述符翻译、绘制重放 |
| **不再需要三份内存** | 代码里可以把主机指针改成真实指针，统一内存的模拟随之消失 | 165 MB/帧 往返、87 ms |

买不到的是：**时间**。上游 95 MB 代码、30 万个函数，L1–L3（编译器工程）一个人能做，L4–L5（运行时与渲染器）要团队。**在头 6–12 个月，这条路线一定比现在能跑的 HLE 更差**——这是必须接受的账。

## 三、已经跑通的第一步（不是 PPT）

`tools/probe.py` —— 只读二进制的 `.pdata` 异常表，不要符号表：

```
.text            95.25 MB
函数数           299,257（覆盖 .text 的 92%）
代码量           88.1 MB，中位函数 117 B，24% 小于 64 B，最大 129,632 B
导入             MSVCP140(113) / CRT / libHttpClient(38) / Bink(23) / xmem(12)
图形边界         没有任何 d3d12.dll / dxgi.dll 导入
```

最后一行是关键情报：**图形不走导入表**（静态链进镜像或经系统 vtable），所以"按符号拦图形调用"不可行——必须在重编译之后按代码位置改。这恰好是重编译相对 HLE 的真正优势。

`tools/lift.py` —— 反汇编 → 生成 C → 本机 MSVC 编译 → 运行 → 与独立解释器差分：

```
可升举子集（无调用、无分支）   119 个函数
差分                        119 / 119 一致（0 差异）
```

覆盖率只有 0.04%，它的意义是**链路通了**：`.pdata` → Capstone → C → cl.exe → 执行 → 比对，全是真实产物。

`tools/oracle/`（Rust）—— **硬件差分**：same ISA ⇒ 原始实现不需要模拟器，把函数字节拷进可执行页、设好 16 个寄存器、`call` 过去、读回来：

```
oracle 自检（mov rax,rcx; add rax,rdx; ret）   rax = 42 ✓
真实函数 vs 生成的 C                            40 / 40 一致
```

这比"两份自己的实现一致"强一个档：裁判是硬件。写这套桩踩到的三个坑，都写进了代码注释——

1. **不能声明 `nostack`**：块里改了 `rsp`，编译器却会按"栈没动"优化，用完的栈槽被 guest 覆盖。
2. **`rbx`/`rbp` 无法声明为 clobber**（LLVM 保留），必须自己在块内保存恢复；其余 14 个用 `clobber_abi("win64")` + 显式 `out`。
3. **RVA 不是文件偏移**：第一版直接按 RVA 从文件里拷字节，跑的是垃圾指令，全部访问违例。要过一遍段表。

还有一个**结构性发现**：`.pdata` 里有相当一部分条目不是函数，而是函数的片段（冷块、funclet），它们的 `ret` 读的是父函数压进去的返回地址。判据可以静态算出——**入口与出口的 `rsp` 位移必须为 0**。这条判据现在是 `tools/diff.py::balanced()`，也是将来正式 lifter 必须带上的。

### 覆盖率到底卡在哪（20,001 个函数采样）

| 原因 | 数量 | 占比 | 意味着 |
|---|---|---|---|
| 以尾调用 `jmp` 结尾 | 12,130 | **61%** | 薄壳与导入桩，**支持"调用"就拿下** |
| 有分支 | 7,794 | **39%** | 需要 CFG 重建 + 标志位模型 |
| SSE/AVX | 60+ | 0.3% | 向量指令族，逐个补 |
| RIP 相对寻址 | 2 | — | 需要镜像基址 + `.reloc` |

**99% 卡在两件事：调用、分支+标志。** 这就是前两层的全部内容。

## 四、实现办法

### 总体结构

```
主机镜像 (.exe/.dll)
   │  probe        读 .pdata 拿函数边界（92% 覆盖）
   ▼
函数表 ──► lifter ──► 每个函数一份 C++（带 CFG、标志位、间接调用表）
   │                        │
   │  差分 oracle ◄─────────┘   同 ISA ⇒ 在本进程里直接 call 原始字节对比
   ▼
recompiled.exe  +  runtime（系统调用层）  +  renderer（图形层）
```

### 五层

| 层 | 内容 | 解锁 | 估时（1 人 + AI 辅助） |
|---|---|---|---|
| **L1** | 尾调用/直接调用、导入桩、RIP 相对 + `.reloc`、子寄存器（eax/ax/al） | 61% 的薄壳 + 大量小函数 | 2–4 周 |
| **L2** | 分支 → 标签 + `goto`、完整标志位（CF/OF/SF/ZF/AF/PF）、`setcc`/`cmovcc` | 再 39% | 3–6 周 |
| **L3** | 硬件差分 oracle（见下） | 正确性可自动化 | 1–2 周，与 L2 并行 |
| **L4** | 运行时层：系统 API 的静态实现 | 能启动 | 2–3 个月 |
| **L5** | 渲染器：提交边界替换，bindless + GPU-driven | **超过 30 fps** | 6 个月+ |

### 三个决定成败的设计选择

1. **不重建 ABI，只重建语义。** 重编译后的函数仍是 `rdi/rsi/rdx/rcx` 那套寄存器约定、仍读写同一块"guest 内存"。这样任何一处未重编译的函数都能回落到原始机器码（同 ISA，直接 `call`），项目可以从第一天就跑起来，而不是等到 100% 才第一次运行。
2. **差分 oracle 是免费的。** guest 与 host 同 ISA，所以"原始实现"不需要模拟器：把函数字节拷到可执行内存，与重编译版本用同一组随机输入各跑一遍，比较寄存器与内存。前作（N64/PSP）要拿整个模拟器当裁判，我们只需要 5 行汇编桩。
3. **图形在提交边界切，不在 API 边界切。** 目标不是"把主机的 D3D12 调用翻译成 PC 的 D3D12 调用"，而是"把这一帧要画什么接过来自己画"。前者注定慢，后者才有机会超过主机。

### L2 的第一刀，以及它撞到的墙（2026-11-26）

`tools/branch.py`：不做全局标志位模型，只认最常见的那一种形态——`cmp`/`test` 后面紧跟 `jcc`。把这一对翻成 C 的比较，其余（`setcc`/`cmovcc`/`adc`/`sbb`/跨函数跳转/间接跳转）一律拒绝。

结果很干脆：

| 指标 | 数值 |
|---|---|
| `.pdata` 里 ≤220 B 的候选 | 207,811 |
| 分支升举器接受 | **121** |
| 其中能独立跑（栈平衡 + 内存安全） | 10 |
| 与硬件差分一致 | **30 / 30** |

**121 这个数字暴露了真正的墙：不是分支，是"调用"。** 采样里 61% 的函数以尾调用 `jmp` 结尾，其余真函数体内也大量 `call`；两者都被拒绝，所以哪怕分支全通了，接受量也只有 121。

结论：**下一步不是把窥孔做得更聪明，而是"闭包升举"**——把被调用的函数一起升举、一起编译、让 `call` 变成 C 里的直接函数调用。N64Recomp 那类项目能跑，靠的就是"全是重编译代码，调用自然解析"，而不是"每个函数独立成立"。这条路需要：

1. 从入口开始做调用图（`call rel32` → 目标 RVA，已在 `.pdata` 里）；
2. 按逆拓扑序升举，生成一份完整 C；
3. 差分时不再"单函数独立跑"，而是链接整份代码后跑入口；
4. 未覆盖的调用（导入、不可达）落到 `call_original(rva)`，由 oracle 那套机制在执行期接住。

### 调用图与函数表（2026-11-26 实测）

单函数独立升举走不通，是因为"调用"；而"调用"恰好也是函数表的最好来源。前 20,000 个函数解码后：

| 指标 | 数值 |
|---|---|
| 会调用别的函数的比例 | **76.8%**（平均 3.0 条出边） |
| 内部调用边 | 45,788 |
| 以尾调用形式出现的内部边 | 7%（3,158）——**"61% 尾调用"说的是入口形态，不是边** |
| **落在 `.pdata` 之外的 `call` 目标** | **94,389 条** |
| 这些目标里在 `.text` 内、可确认为函数起点 | **50,103 个** |
| 间接调用 | 15,760（**18%**），其中 `[rax]` 11,178（虚表） |

于是一个纯机械的改进：**`call` 的目标就是函数的第一条指令**。以 `.pdata` 为种子，把 `call`/`jmp` 的目标加进函数表，再解码新增的，再取新边，直到不再增长：

```
.pdata           299,257 functions
round 1:         +20,121 function starts from call targets   (只用了 6,000 个种子)
round 2:          +3,544
function table   315,990 functions   ← 16,733 个起点是 .pdata 没写的
```

这解释了 `.pdata` 那 8% 的缺口是什么：**没有展开信息的叶子函数**，也就是每次 `call` 都会撞上的那批。它们不能靠"扫描空隙"猜，只能靠调用边反推——而且反推是确定的，不是启发式。

闭包规模（深度 4，从连接度最高的入口起算）：728 / 667 / 328 / 86 / 73 个函数。这个量级说明**闭包升举是可行的**：一份 C 里几百个函数，链接一次就能跑，不需要"全 30 万函数都翻译完才能第一次运行"。

### 子寄存器、绝对地址与映像映射（2026-11-26）

三件事一起做，因为它们是同一个"操作数宽度"问题的三个面：

1. **子寄存器**。写 `esi` 会把 `rsi` 高 32 位清零，写 `al` 保留其余 56 位，写 `ah` 是 8 位偏移 8。
   用 `(uint32_t)` 强转近似会得到"小正数全对、其他全错"的代码，所以按宽度与位移建模：
   `wr()` 对 32 位生成 `r[i] = (uint64_t)(uint32_t)(expr);`，对 8/16 位生成读-改-写掩码。
   内存操作数同样按 `op.size` 落宽度——`mov dword [rbp-4], eax` 写 8 字节会把相邻局部变量抹平。
2. **`movabs`**。capstone 对 `mov r64, imm64` 报的助记符是 `movabs`，之前整条拒绝；580 个函数卡在这。
3. **`[rip + d]`**。这是 image 里的固定位置，升举期就能算出来，于是变成 `img + rva` ——
   一个真实的主机指针。前提是**映像真的被映射在首选基址**（`0x140000000`，`SizeOfImage = 0xB06D000`），
   所以 `tools/lift.py` 现在会生成一段加载器：`VirtualAlloc` 到首选基址 + 按段表逐段 `ReadFile`。
   不用 `MapViewOfFile`：文件映射是文件布局，`SEC_IMAGE` 不是，而 RVA 指的是后者。
   同一个道理适用于立即数里的绝对地址——落在映像范围的 `imm64` 也要跟着映像重定位。

结果（前 40,001 个函数，`tools/cover.py`）：

| 指标 | 之前 | 现在 |
|---|---|---|
| 分支通道接受 | 9,331（23.3%） | **12,723（31.8%）** |
| 拒绝面首位 | 间接调用 7,829 | 间接调用 7,829 |
| 新暴露的拒绝面 | — | `segment` 1,004、`div` 676、`vxorps` 1,369 |
| SIMD 合计 | 15,203 | **9,624**（`vmovaps` 6,869 / `vmovss` 1,386 / `vxorps` 1,369） |

**但是：加了 rip 之后，一个带 rip 的函数也没进得了差分。** 这不是实现错，是 harness 的结构问题——
见下一节。

### 差分 harness 的天花板（2026-11-26 实测）

| 指标 | 数值 |
|---|---|
| `--limit 400` 升举成功 | 148 |
| 其中"能跑"（栈平衡 + 内存不越界） | **10（2.5%）** |
| 用 `[rip+d]` 的函数（前 60,000 个里） | 8,001 |
| 其中直线型 | 32 |
| 其中栈平衡 | 3 |
| 其中能进 harness | **0** |

原因就一句话：**现在的内存模型是 `stk + (addr & 255)`**——把所有内存都当成那个 256 字节栈。
真实函数第一件事是 `mov [rcx], rax`（写调用方给的缓冲区），在 oracle 里就是访问一个 256 字节栈
之外的地方，直接违规；于是 `safe()` 只能把这类函数全滤掉，剩下的恰好是"只碰自己栈帧"的那 2.5%。

这不是能靠放宽过滤器解决的问题：`& 255` 是拿低位当偏移，本来只在"地址恰好落在栈附近"时才对。
**正确的模型是 guest 指针就是 host 指针**：映像映射在首选基址、堆由 CRT 分配、`*(uint32_t*)addr`
不做任何变换——X2W 就是这么做的（映射 PE、真指针）。改造清单：

1. `lift.py`：内存操作数去掉 `stk` 与 `& 255`，直接 `*(uintN_t *)(uintptr_t)(addr)`；`push`/`pop` 变真内存写；函数签名从 `(r, stk)` 回到 `(r)`。
2. `oracle`：栈与 arena 都 `VirtualAlloc` 在**固定地址**，两侧同址，才能逐字节比。
3. 差分：参数寄存器指向 arena，比的不再是"256 字节栈"，而是 arena 的哈希（X2W 的"逐字节比输出"）。
4. 这样构造函数、setter、虚表写这类函数才第一次可测——它们占真实代码的多数。

在那之前，`12,723` 这个接受量是**未验证**的：能证明一致的是那 10 个（30 例）；其余是"翻译出来了，但还没有裁判"。
