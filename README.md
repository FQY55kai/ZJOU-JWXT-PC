# 静态重编译研究：Xbox Series X|S → Windows x64

> 仓库代号 `ZJOU-JWXT-PC`。

把一个 x86-64 主机镜像里的**机器码离线翻译成可编译的 C**，再由宿主编译器生成原生可执行文件。不解释、不在运行时翻译二进制；原文的语义由**硬件本身**做裁判。

本仓库只有工具与文档，**不含任何游戏数据、密钥或反编译产物**。使用者需自备依法获得的副本。

## 1. 结论先行

| 问题 | 答案 |
|---|---|
| 这条路能省掉什么？ | **省不掉"翻译"**——guest 与 host 同为 x86-64，没有翻译红利。买到的是：可编辑的代码、整体替换图形边界、消掉三份内存 |
| 现在做到哪一步？ | 前 40,001 个函数里 **39,922（99.8%）** 能翻成可编译的 C，整张 299,257 条函数表上 **298,606（99.8%）** 能过 |
| 翻译对了没有？ | 用**原始机器码直接 `call`** 做裁判，`xmm0-15` 与 16 KiB arena 一起比：整函数 **125 例里 124 例（99.2%）逐寄存器、逐字节、逐向量寄存器一致**；另有**指令级 147 条 × 4 例 = 584 例全部一致** |
| 最缺什么？ | **环境**，不是翻译。204 / 264 个可运行函数在两侧同样崩溃——它们读的全局在文件里是 0，只有游戏自己的初始化代码才会写 |

## 2. 方法：四步

```
PE 镜像 ──① 取边界 ──► 函数表 ──② 升举 ──► C 源码 ──③ 编译 ──► .exe
                    (.pdata)         (capstone)      (cl.exe)
                                          │
                                          └──④ 裁判：原始字节 call 过去，读回来比
```

1. **取边界**：`.pdata` 的 `RUNTIME_FUNCTION` 数组（12 字节：起/止/展开信息）免符号表给出 299,257 个函数，覆盖 `.text` 的 92%。剩下 8% 是**没有展开信息的叶子函数**，用 `call` 目标反推补全——目标就是函数的第一条指令，迭代到收敛，长到 **315,990**。
2. **升举**：每个函数 `void f(uint64_t *r)`，`r[0..15]` 是 rax..r15。操作数按自身宽度读写（写 `esi` 清零高半、写 `al` 保位、`ah` 是偏移 8）；`[rip+d]` 在升举期就折成 `img + rva`；调用另一个升举函数**不需要 marshalling**，因为两边共用同一个寄存器文件。`call` 会先把返回地址写进 `rsp-8` 并把 `rsp` 降 8——和硬件逐字节一致，否则被调函数建的整个帧都偏一格。
3. **编译**：MSVC。生成的是普通 C，不是 IR——能不能过编译器是最低门槛。
4. **裁判**：同 ISA 意味着原实现不需要模拟器。**guest 指针就是 host 指针**：映像映射在它的首选基址、arena 映射在固定的 `0x20_0000_0000`，于是 `mov [rcx], rax` 两侧都是"存到 rcx 指向的地方"，比较的是 16 KiB arena 而不是一个折叠地址的临时缓冲区；`xmm0-xmm15` 同样两侧各带一份 512 字节的向量文件进出。95.5% 的升举函数含 `call`，所以未升举的目标走 [`guest_bridge`](tools/oracle/src/lib.rs)——和裁判同一个调用桩——把**被测函数**换成 C，它下面调用的仍是游戏自己的代码。

## 4. 三条被数据否定的路线

写在这里，是因为它们看起来都更省事。

**① 单函数独立成立。** 分支升举器只接受 121 / 207,811——墙不是分支，是调用。一个函数调另一个函数，单函数独立这条路本身就走不通；把两边一起翻，`call` 就变成 C 里的直接调用。

**② 把上游 82 个提交 cherry-pick 进来。** 结果是 **82/82 全冲突**，而且不是"冲突多"：本树把 `bindless.rs` 拆成 `descriptor/*`，上游对它的改动是 delete/modify（0 个冲突块）；其余改动各自挂在它自己的前置设施上（每堆写标记、内存记账）。**结构上不可移植。**

**③ 运行时翻译（HLE）路线的账本。** 世界场景稳态 5.0 fps = 200.7 ms/帧，其中命令录制 149.1 ms、主机内存↔宿主副本 86.8 ms。这些在主机上是 0——统一内存 + 硬件直接消费绘制包。这就是为什么要走到编译期。

## 5. 验证：比 16 个寄存器更多

`39,922` 是**翻译量**。能被证伪的才是**验证量**，两者之间隔着"这个函数跑不跑得起来"。

裁判这边有四样东西是"一致"这个词的前提，缺任何一样都会让结论变成一句空话：

**① 向量寄存器进比较。** 之前只比 16 个通用寄存器与 arena。但这批函数里几乎每一个的序言都是
`vmovaps [rsp+0x28], xmm6`——MSVC 把 `xmm6-xmm15` 当非易失寄存器，进出都溢出。只要 `xmm` 不进比较，
"溢出写对了没有"就只能靠 arena 间接看到，而"恢复到了哪个寄存器"根本看不到。现在两侧各带一份
**16 × 256 位**的向量文件进出记录，`v[16][4]`，按 `memcpy` 在操作数自身宽度上搬运——因为
`vmovaps` 就是一次字节拷贝，不是一个"数"。VEX 编码的 128 位形式会把目标的高 128 位清零，这一条也建模了：
同一个寄存器后面可能按 256 位读。

**② 逐例故障恢复。** 一半函数会读文件里为 0、只有游戏自己初始化才写的全局，`mov rax,[rip+G]; mov ecx,[rax+0xBF4]`
在任何翻译发生之前就是一次访问违例。原来这会让整批用例连同进程一起死，驱动只能二分定位——每个出事的
用例重跑六轮、每轮重新映射 176 MB 镜像，一次两分钟的比较变成十五分钟。现在两侧都用
`setjmp`/`longjmp` + 向量化异常处理器把故障收回本用例：**崩溃是一个用例的结论，不是一批的中断。**

**③ 一条被差分抓出来的真错。** `cmp ecx, -2; jb` 这种"`(x-2) > 1`"的边界判断，
立即数到位后是**符号扩展到 64 位**的，而比较按 64 位无符号做——于是 `ecx = 0xFFFFFFFE` 被判成
"小于"`0xFFFFFFFFFFFFFFFE`，硬件判"不小于"。整条路反了。修法是把两侧都截到操作数宽度再比：

```python
return f"((uint{bits}_t)({a}) {UNSIGNED[suffix]} (uint{bits}_t)({b}))"
```

这不是"多加一条指令"，是**只有硬件裁判才会发现**的那类错误：解释器和发射器都从同一份理解出发，
两边会一起错、一起同意。抓到它的函数 `0x2839d0` 全部工作就是这一个判断。

同一类错误还有第二处，也是这一轮才被抓出来的：**相等比较没有截断**。`cmp eax, -1` 比的是
`0xFFFFFFFF` 与 `0xFFFFFFFF`，相等；而快照是 64 位的，比的是 `0x00000000FFFFFFFF` 与
`0xFFFFFFFFFFFFFFFF`，不等。于是 `setne al` 把 1 写进了本该是 0 的字节：

```
0x7c62b0: rax: hw 0xffffff00 vs c 0xffffff01
```

这个函数从头到尾只有 41 字节，工作就是 `cmp eax, -1; setne al`。修法与上一处一行之差——
两侧都截到操作数宽度：

```python
return f"((uint{bits}_t)({a}) {EQUALITY[suffix]} (uint{bits}_t)({b}))"
```

上一轮列出的 `0x272070` 是**同一个签名**（`0xffffff00` vs `0xffffff01`），所以大概率是同一个 bug；
但它只有在成批跑时才能比（单独跑会读到本批前一个用例在映像全局里留下的状态，两侧同样崩溃），
而批次内容随接受量变化已经不同，这一轮没能再观察到那次不一致——按"没观察到"记，不按"已修好"记。

**④ 间接调用不再拒绝，改成一次运行期查表。** 这一轮最大的一块是 7,861 个函数的**唯一**障碍是
`call rax`（或 `call [rcx+0x18]`）：目标是个值，静态期无从解起。做法不是猜，而是承认它就是一次查表——

```c
uint64_t t = <操作数，在压栈之前读>;
*(uint64_t *)(uintptr_t)(r[4] - 8) = (uint64_t)(img + <返回地址>);
r[4] -= 8;
call_indirect(r, t);
r[4] += 8;
```

`call_indirect` 与 `jump_indirect` 是这个模块对外的**两个钩子**（`tools/branch.py` 的模块注释里写着契约：
`target` 是 guest 自己的地址，返回地址已压、`r[4]` 已降）。生成的派发表按 RVA 分发到已升举的函数体，
查不到就跑那里的原始字节——**不是降级**，那就是主机上跑的同一段代码。两个钩子而不是一个，因为栈协议不同：
`call` 之后 `ret` 要回到这里，尾跳转之后不用。

操作数必须在压栈**之前**读：`call qword ptr [rsp+0x28]` 读的是返回地址**上面**那一格，硬件先算操作数再写返回地址。
这条顺序错了，在差分里表现为"某个槽整体错位 8 字节"。上一轮那个 `0x2ec3d0`、这一轮的 `0x7c0bf0`
都是这个形状，但**没有确证是同一个原因**：帧偏移差 8 也可以来自 `push` 与影子空间的重叠、或一次
`rsp` 的对齐调整——形状相同不等于原因相同。

**⑤ 一条指令的裁判：把函数切成一条指令。** 整函数是证明*函数*对的单位，是证明*指令*对的错单位：
用 `vpsignb` 的那些函数里，多数会去读一个文件里为 0 的全局，于是两侧一样崩，
这条指令从头到尾没有被执行过。这一轮新增的六十个点里有六成会这样白白过去。

所以 `diff.py --snippets` 给每条指令单独造一个函数：**字节直接从映像里抄**（不写汇编器、不手搓操作数，
编译器选了什么就测什么），写进 `.text` 里一段无人拥有的填充区，后面接 `ret`；只通过标志说话的指令
（`vtestps`、`cmp`）再接四个 `setcc`（`r10b`..`r13b`，没有任何片段的操作数用到这四个）。
这些都写进**映像的一份副本**，两侧映射同一个被打补丁的文件——**字节就是两边的规格说明**，裁判没有机会
测到移植侧不执行的东西。于是比较项仍然是"16 个通用寄存器 + arena + 向量文件"，却不需要 `--limit`、
不需要挑函数：现在 **147 条指令 × 4 例 = 584 例，全部一致**（`--rounds 6` 时是 882 例）。

它抓到三个整函数差分抓不到的错，三个都不是"少写一条指令"：

**（a）`vtestps` 的 CF 与 ZF 被写反了。** 原先按"CF = AND 为零、ZF = ANDNOT 为零"接线，SDM 是
**ZF = `(SRC1 AND SRC2) == 0`、CF = `(SRC2 AND NOT SRC1) == 0`**：与落进 ZF，与非落进 CF。
更麻烦的是 VTESTPS/VTESTPD **只比符号位**——"bitwise comparison of all the **sign bits** of the packed
elements"，不是整字的与。两条错叠在一起时它看起来是对的：编译器最常见的写法是 `vtestps x, x`，
这时两个公式给同一个答案（ZF=1、CF=1）；换成两个不同的寄存器、符号位一正一负，就整条反了。
定位方法是给硬件喂四个互不相同的寄存器（`xmm2=1`、`xmm3=2`，正负号各一组），看哪一组 (CF,ZF)
对得上——不是推理，是查表：

| 指令（`xmm3` = A，`xmm2` = B） | A | B | 实测 CF | 实测 ZF | 按 SDM 的算式 |
|---|---|---|---|---|---|
| `ptest` | 2 | 1 | 0 | 1 | ZF=`(A&B)==0`=1，CF=`(B&~A)==0`=0 |
| `vtestps` | 2 | 1 | 1 | 1 | 符号位与=0 → ZF=1，符号位与非=0 → CF=1 |
| `vtestps` | `0xFFFF…` | `0xFFFF…` | 1 | 0 | 符号位与≠0 → ZF=0，与非=0 → CF=1 |

**（b）对着一条通道的*值*取地址。** `vtestps` 要逐字节读操作数，写成了 `(const uint8_t *)v[3][0]`——
把寄存器里那一格的**值**当成了地址。硬件侧不崩、移植侧崩，差分报"只在移植侧崩 2 例"；改成
`lane_ptr()`（取那一格的地址），并让 `lane_at()`（取那一格的值）保持原样：两个函数、两个用途。

**（c）`test` 的 ZF 不是第一个操作数的。** `test byte ptr [rcx+0xb0], 1` 在那一字节是 2 时 ZF 为 1；
按 `a != 0` 接线则恒为"非零即真"，于是整条位测试方向反了。这一个是在**整函数**差分里露头的：
`0x7d80` 只差两个寄存器，硬件把 `ecx`/`edx` 都置成 0x20，移植侧原封不动——说明它走了另一条路，
而分歧点就是那一条 `test …, 1`。改成先截到操作数宽度再与，141 例里的一致数从 132 涨到 138。

顺带一条纯增量：`setcc` 写的是**字节，不是标志**，所以 `cmp a,b / sete al / setb cl` 是编译器的常规输出。
原先 `setcc` 一执行就把 `pending` 清掉，第二条只能被拒；现在它留到真正写标志的指令为止——这一条
（加上 `vpblendd` 的键名少写一个 `p`、`vmovddup` 的访存源）就是 30,232 → 32,593 的来源。

### ⑥ 一条文档推不出来、只有硬件能定的语义

`vfmadd132ss xmm3, xmm1, xmm1` 这类**标量**融合乘加，结果的 `127:32` 从哪儿来？
按"VEX 标量算术都取 `SRC1`"的直觉，答案显然是 `xmm1`。实现照此写了，指令级差分直接给了 **0/6**：

```
0x5661062: vfmadd132ss   x3[0] hw=a829c23e9b2dc73f / c=a829c23e9d3d7bf
```

低 4 字节（`a829c23e`）两侧一致，错的全在上面 12 字节。三个互不相同的用例给出同一个结论：
`127:32` 等于**目标寄存器原值**，与 `SRC1` 无关。`vfmadd213ss xmm2, xmm3, xmm5`（目标是
全零寄存器）与 `vfmadd231ss xmm1, xmm0, xmm0`（目标是负号寄存器）各自复现了一次。
把 `memcpy(src1)` 换成"什么都不做、只盖低 4 字节"之后 6/6。

同一条路线上还有两处**别名**，都是差分逼出来的，不是想出来的：

| 形态 | 错法 | 后果 |
|---|---|---|
| `vpackssdw ymm3, ymm4, ymm3` | 边读源边写目标 | 目标就是第二个源，高半读到的已经是被盖掉的值 |
| `vinserti128 ymm7, ymm8, xmm7, 1` | 先把源寄存器整个搬进目标 | 要插入的那个 `xmm7` **就是目标**，搬完再读是读自己的新值 |

两处的修法一样：**先把要用的字节全读到栈上，再动目标**。`vpshufhw xmm9, xmm9, 0x1b` 是第三例。

### ⑦ 标志是**状态**，不是条件

上一轮的原则是"消费者在另一个块里时，只有该块所有入边留下**同一个** token 才继承"。同一个 token
意味着同一条产生指令跑过、快照是同一批变量，所以取哪条路都是同一个值——这一条留着，判据从
"入边数 == 1"换成了"所有入边的出口 token 相同"，更宽松也仍然诚实。

两条路留下的 token **不同**时（`cmp eax, 3` 一条、`test r9, r9` 另一条），上一轮是拒绝。
但硬件上 EFLAGS 本来就是一个寄存器：**每条出口走之前把它写下来，块首按变量读**，跑的就是同一条机器。
所以合并点的 token 是四个变量：

```c
uint8_t fz_2925 = 0, fs_2925 = 0;          /* 声明放在函数最前面，见下面 (b) */
...
/* 出口 0x2922（cmp rax, rcx，落进 0x2925） */
fz_2925 = (uint8_t)(((uint64_t)(pa_2922) == (uint64_t)(pb_2922)));
L0x2925: ;
/* 出口 0x2a96（jmp 0x2925）在它自己的 goto 之前写同一个变量 */
```

两条规矩把这个做法按在"不猜"的范围里：

- **能用交集才合并。** 每个 token 只承认它能回答的那几位（`kept_flags` 就是拿 `condition` 一位一位去问，
  问不出来就是没有）。合并点保留的是所有入边的**交集**；消费者要的那一位不在交集里，就照旧拒绝——
  `tzcnt` 的 SF 是未定义，所以"合并点 + `js`"这种组合仍然过不去。
- **没人的时候不干活。** 合并点先做一遍需求分析（消费者要哪几位、再沿合并点自己的入边往回传），
  没有读者的合并点整个撤掉，否则每个交叉口都会多出四条赋值。

实现里有两个坑，都是先写错再改的：

**(a) 赋值必须落在标签之前。** 第一版把"落进块首"那条出口的赋值插在标签**之后**，于是从别处
`jmp` 进这个标签时会先执行它——用上一个块留下的 `pa_2922` 去算一个跟这条路径无关的值。
标签是**别人跳进来的入口**，落进它的那条边只能在自己那一侧写。

**(b) 声明必须在最前面。** 回边的赋值在文本上晚于它喂的那个块（`jmp 0x58c00` 在 0x58d66，而
0x58c00 在前面），C 要求先声明后使用，所以四个变量统一声明在函数体开头。

顺带修掉一个更早就存在的错：`flag_step` 里"这条指令改没改标志"那道门写在了"这条指令**产生**
标志"之前，于是 `xor eax, eax` 被当成破坏者，它的 ZF 过一条边就没了——块首的 `cmove` 报
"without a compare"，而真正的原因在查表顺序。这个错只值 2 个函数，但它是**镜像写错**的典型：
`flag_step` 是发射侧那段记账的镜像，两边不一致时，报出来的是消费端的症状。

### ⑧ 片段差分抓到的五处

整函数差分看不见它们：用到这些指令的函数大多会去读一个文件里为 0 的全局，两侧一样崩。
把它们各自切成一条指令之后，几处都是**0/4 或 0/5** 这种一眼能认的形态：

| 指令 | 错法 | 现象 |
|---|---|---|
| `vcvtpd2ps` / `vcvtps2pd` / `vpermilpd` | VEX 的 128 位形式把 `255:128` 清零，只写了低 128 位 | 三处 `x[2]`/`x[3]` 不一致 |
| `vaddsubps` | 偶数通道写成**加**（SDM 从 `DEST[31:0] := SRC1 - SRC2` 起头） | 整个 `x[0]`/`x[1]` 不一致（0/4） |
| `blsi` | 按"进位 = 源是零"接线 | 硬件留下的是**进入时**的 CF（源不为零却是 1）——说明这一位未定义，改成只承认"溢出清零" |
| `tzcnt`/`lzcnt` | 拿**结果**为零当 equality（源为零时结果是位宽） | 用 `src == 0` 才对 |
| `vpsrldq`/`vpslldq` | 照 legacy 形式写成"就地移"，而 VEX 形式的目的寄存器不是源 | `x5` 与 `x2` 无关，0/4；必须先 `memcpy` 一格再移 |

最后一条是这一轮新抓的，也是最值得记的一类：legacy 的两操作数形式让"就地修改"成为可行的实现，
而同一段代码被 VEX 的三操作数形式复用时就悄悄错在**没读第二个操作数**。这一点**整函数差分永远发现不了**
——用到 `vpsrldq` 的十个函数里，目的寄存器恰好都等于源。

### ⑨ 白名单漏一项，报错报在**消费者**身上

标志模型里有两张表：谁**写**标志（`FLAG_FROM_RESULT` 与几条专门的规则），谁**不写**（`FLAG_SAFE`）。
第二张表是手工维护的，漏一项的后果不是"算错"，而是**把比较作废**：`cmp / <漏掉的那条> / cmovcc`
走到 `cmovcc` 时已经没有 token 了，于是报 `cmovbe without a compare`——**报的是消费者，错的是白名单**。

这一轮就是这么发现的：探针把"被拒绝的那条指令"从异常回溯里取出来（而不是从消息里猜助记符，
第一版猜错过，见 §5 的探针注释），一眼看到 `cmp di, r14w / rorx ecx, eax, 0x10 / cmovbe ecx, eax`。
`rorx` 是 BMI2 的循环右移，**不写标志正是它与 `ror` 的全部区别**，连 §7 都引了 SDM 那一句，
可它不在 `FLAG_SAFE` 里。补的时候顺手把同类的漏项一起补上：`movbe`、三道栅栏、`clflush`、
`vzeroupper`/`vzeroall`、`prefetch*`（预取按前缀判，因为助记符有六个）。

同一个探针还给了另外两处——`bzhi` 与 `mul` 的标志**有定义但从没建模过**：

| 指令 | SDM 给了什么 | 之前的行为 |
|---|---|---|
| `bzhi` | ZF/SF 是结果的；CF 是"索引 ≥ 宽度"（一位都没清）；OF 清零；AF/PF 未定义 | 整条当破坏者，`je` 直接拒绝 |
| `mul`/`imul` 单操作数 | CF = OF = "高半里有超出低半的东西"（无符号看非零，有符号看符号扩展）；其余四位未定义 | 同上，`seto dl` 直接拒绝 |

两条现在都按"**未定义就是拒绝**"落地：`mul` 之后 `jz` 仍然拒绝（ZF 未定义，跳过它是猜），
只有 `jb`/`ja`/`jo`/`jno` 这一类能过。这与上游 `cpu_bmi1_logic_aot` 注释里的态度一致
（"Reading an undefined flag before a subsequent flag-defining instruction is rejected"）。

### 一条不能装作没看见的边界：`gs:`

`gs:[0x58]` 是 TEB 里的 TLS 数组指针，而 **TEB 是每进程一份**。裁判和移植是两个进程，那个指针指向
两个不同的对象，从它出发的一切——TLS 块、标题放在 TLS 里的分配状态——两侧毫无关系。这类函数翻译得没错，
但在这里**不可能**得到一致的结果。所以它们被单独计数，不算进一致率，也不算进不一致：这是**量具的边界**，
不是翻译的缺陷。一个真正脱离了裁判的移植版本只有一份 TEB，那时它是自洽的。

同样的道理适用于 IAT 里解析出来的函数地址：跨进程不同，被存进 arena 就会成为差异。
以及 `MXCSR`：整个 `.pdata` 里只有一对 `vldmxcsr`/`vstmxcsr`，所在函数我们正确拒绝、留在桥后面，
所以舍入模式与 DAZ/FTZ **没有作为状态进差分**。函数自己存了再恢复就没事；改了不恢复就会像 TEB 一样
落到"两个进程各自的 MXCSR"上。收掉它要让这两条进模型，并把 MXCSR 记进用例记录。

### 桥：唯一的"作弊点"，也是唯一的可行点

95.5% 的升举函数含 `call`。如果裁判只能进入叶子函数，可测比例的上限就是 0.5%——实测 20,000 个函数里
只有 30 个不含 `call`。所以未升举的目标通过 `guest_bridge` 调回原始字节：

```c
void f_0x4f862d0(uint64_t *r) {          /* 未升举：走桥 */
    r[4] += 8;                            /* 升举侧已经压过返回地址，先还原 */
    note(r[4] - 8);                       /* 桥会在这里压一个宿主地址，记下来 */
    guest_bridge(r, v, img + 0x4f862d0);  /* v 是向量文件，一同交出去 */
    r[4] -= 8;
}
```

桥和裁判是**同一份内联汇编**（`tools/oracle/src/lib.rs` 的 `call_guest`），所以被测函数之上是 C、
之下是原码，连 `xmm6-xmm15` 的溢出与恢复都是同一段代码。唯一对不上的只有那个 8 字节槽：硬件压的是映像地址，
桥压的是宿主地址。移植侧把槽位报给裁判、裁判跳过它——不是"差不多就行"，是**精确地少比一个已知会不同的 8 字节**。

### 这批的账

`--limit 400 --branches --rounds 3`（`--timeout 5`，从 `.pdata` 第 0 条起）：

| 指标 | 上一版 | 现在 |
|---|---|---|
| 升举成功 | 300（`--skip 20000`） | 400（从第 0 条起，换了一批函数） |
| 能进差分（在 arena 里跑得完） | 190 | **265** |
| 真跑出可比结果 | 59 个函数 / 80 例 | 54 个函数 / **125 例** |
| 逐寄存器 + 逐字节 + 逐向量寄存器一致 | 78/80（97.5%） | **124/125（99.2%）** |
| 两侧同样崩溃 | 130 | **208** |
| 只在移植侧崩溃 | 1 | 3 |
| 碰 TEB，单独计 | 41 例 | 43 例 |

这一轮把同一批函数在**改动前**（`HEAD` 的独立工作树）又跑了一遍做对照：两侧都是"3 例只在移植侧崩、
1 例不一致"，可比的例子从 122 涨到 124。也就是说这一轮新增的接受量**没有带进新的不一致**——
那 4 个是原来就有的（`0x18dc0` 那一类帧内返回地址，见下）。

换样本是不得已：样本的定义是"从第 N 条起前 K 个能被接受的函数"，同一条命令在两轮里选中的已经是
不同的函数。所以能横向比的只有**一致率**，而它是在比较项没变（16 个通用寄存器 + 16 KiB arena +
16×256 位向量文件）的前提下从 97.5% 到 97.9%，而且这一轮的一致率是**先修掉 9 个不一致**换来的
（`test` 立即数那一条，见 §5⑤c）。

**1 个函数不一致，留在这里没有绕开**：

| 函数 | 现象 | 方向 |
|---|---|---|
| `0x18dc0` | 栈上 `+0x1f58` 与 `+0x1f60` 两个槽互换：硬=`0x2000000e70`/宿主地址，移=宿主地址/`0x2000000c90` | 一次 `push` 与影子空间重叠，帧内偏移差 8；帧里存的是**返回地址**，而那一格经 `guest_bridge` 与直接 `jmp` 进来的地址天然不同 |

这个差异这一轮又单独验了一次：把本轮的 ALU 标志改动整体关掉重跑，输出逐字节相同——**不是这一轮引入的**，
是桥的固有痕迹（帧里那一格是返回地址，硬件拿到的是原调用点的地址，桥拿到的是桥自己的）。

`0x7d80` 与 `0x49700` 这一轮都修好了：它们的分歧点是 `test byte ptr […], imm`，
见 §5⑤c。上一轮列出的 `0x7c0bf0`、`0x272070` 在新样本里不再出现——按"没观察到"记，不按"已修好"记。

一条顺带学到的性质：**用例之间不是独立的**。映像映射在进程里，前一个用例写过的全局会留给下一个；
这也是某些函数只能成批比、单独跑必然"两侧同样崩溃"的原因。差分比的是"同一次运行里两侧是否一致"，
不是"这个函数对任意输入是否一致"——这两句话不是一回事。

### 剩下的墙

其余 **201** 个**在两侧同样崩溃**——它们读的是游戏初始化代码才会写的全局，不是翻译错了。
这是"单函数独立成立"这条路的尽头，再往上只能整份链接后跑入口（见[路线图](docs/roadmap.md) M1.5）。

## 7. 参考与引用

两条关键规则不是我们发明的，来自目前唯一公开自述"x64 机器码 → C++ 静态重编译"并持续开发的项目：

1. **Xbox2Windows**（R0Y00，MIT）— <https://github.com/R0Y00/Xbox2Windows>
   - 标志位只在"生产者 → 消费者、且该直线段无其他入边"的范围内建模；`Jcc`/`SETcc`/`CMOVcc` 是消费者，`mov`/`lea`/`not`/`bswap`/`push`/`pop`/`cbw`/`cwde`/`cdqe`/`cqo` 不破坏标志。见其 `tools/cpu_switch_aot.py` 的模块注释。
   - 跳转表只接受两种形态，且基址必须在每条路径上是**同一个 RIP 相对地址**、索引必须被证明**等于参与比较的值**；`BT/BTS/BTR/BTC` 的位偏移对寄存器基址取模到操作数宽度。
   - **只顺着边遍历，不线性扫描**——MSVC 把跳转表放在 `jmp` 之后，线性扫描会把表本身当成代码。本仓库 `tools/branch.py` 的 `walk()` 即此规则。
   - 本轮把它的"生产者 → 消费者"规则向前推了一步：`ucomiss`/`vucomiss` 也是标志的生产者，`andn`/`bextr` 也是（前者供 SF/ZF，后者只供 ZF、清 CF/OF），而整套向量搬运与位运算**不碰标志**——所以 `cmp` 后夹一次 `vmovaps [rsp+0x28], xmm6` 再 `jz` 仍然合法。前者是我们自己按 SDM 推的，X2W 的 `cpu_switch_aot.py` 只覆盖整数部分。
   - 本轮拉到上游 `fbe249f6`（44 条新提交，CPU 侧 3 条）：`bb1addf2` 升举 `VHADDPS/PD`·`VHSUBPS/PD`·`VADDSUBPS/PD`，`780c0bc4` 升举 BMI2 的 `BZHI`·`MULX`·`PDEP`·`PEXT`，`d371ce46` 补 VEX.256 的跨通道扩展与 dword/qword 解包。水平加减与解包本仓库已有，**`VADDSUBPS/PD` 缺**——按 SDM 补上后片段差分判它 0/4（§5⑧），正好说明这条为什么值得单独测。`PDEP`/`PEXT` 在这个映像的拒绝面里**一次都没出现**（不到 3 个函数），所以记在这里、不写代码：一份用得上的实现比一份"看起来完整"的表有用。
2. **XenonRecomp**（hedge-dev，MIT）与 **N64Recomp** — 闭包式重编译的先行者：函数边界从调用边反推、跳转表转 `switch`、"翻译整份代码再链接"而不是逐函数独立成立。
3. **VIctory**（Marvisak，GPLv3）、**XCL**（ivall）、**Palmetto**（luizwidmer）— 运行时翻译（HLE）路线的对照实现。本仓库**未使用其代码**；§4③ 的性能账本来自对它们的实测（另：同一台 RTX 4080 Laptop 上，VIctory 于第 194 帧设备移除，四个 fork 存活——说明那是该实现的问题，不是平台限制）。
4. **Intel® 64 and IA-32 Architectures Software Developer's Manual** — 指令语义与标志位定义的最终依据。这一版具体靠它的是：
   - **Vol. 2A `MOVSS`/`MOVSD`**：*register* 形式复制全部 128 位，*memory* 形式把源以上全部清零——同一个助记符两种语义，所以本仓库**拒绝** legacy 的寄存器形式而不是猜它（`tools/lift.py` 的 `vec_line`）。
   - **Vol. 2A `VMOVSS`**：三操作数形式取 `SRC2` 的低字段 + `SRC1` 的 `127:32`；VEX 编码的 128 位形式把 `255:128` 清零。这一条必须建模——同一个寄存器后面可能按 256 位读。
   - **Vol. 2A `UCOMISS`/`UCOMISD`**：无序时 `ZF=PF=CF=1`、大于时三者全 0、小于时只置 `CF`、相等时只置 `ZF`。§5③ 的 7 个不一致里有一个就是它前面的分支。
   - **Vol. 2B `BEXTR`**：起止位打包在一个操作数里，长度越过顶端时"取剩下全部"而不是回绕。
   - **Vol. 2B 移位计数**：按目标宽度掩码（`shl eax, 32` 是空操作，不是 32 位移位）。
   - **Vol. 2A `BLENDPS`/`BLENDPD`/`PBLENDW`/`VPBLENDD`**：立即数的第 `n` 位选**第 n 个通道**，通道宽度由指令决定（32/64/16/32 位）——整个操作是**按位选择**，不是浮点运算。这一条让 `vblendps` 不需要浮点模型就能翻译（1,277 个函数）。
   - **Vol. 2A `CMPPS`/`CMPSS` 的八种谓词**：`EQ_OQ`/`LT_OS`/`LE_OS`/`UNORD_Q`/`NEQ_UQ`/`NLT_US`/`NLE_US`/`ORD_Q`。前三个是**有序**的（NaN 时为假，正好是 C 的 `==`/`<`/`<=`），中间三个是**无序**的（NaN 时为真，正好是那三个的否定），后两个直接就是 `isnan`。写错一处，编译器用来捕 NaN 的那对指令就全反了。capstone 把谓词折进助记符里（`vcmpeqps`）、并不再报立即数，所以名字要拆开读（`tools/lift.py` 的 `cmp_form`）。
   - **Vol. 2A `PCMPEQB`/`PCMPGTB` 等**：结果是**全 1 或全 0 的掩码**，不是 0/1 的布尔；`pcmpgt*` 是**有符号**的，而且 8 位与 16 位根本没有无符号形式（惯用法是先 `xor 0x80`，标题自己会做）。
   - **Vol. 2A `UNPCKLPS`/`PUNPCKHWD` 等**：低/高半的**交错**，且 256 位形式是**每条 128 位通道各自重复**，不是跨通道。写成跨通道会让 `vpunpckhwd ymm` 的高半全错。
   - **Vol. 2A `HADDPS`/`HADDPD`**：每 128 位通道内先把自己的一对折叠掉、再折另一个源；`haddpd` 的两个输出分别来自两个源（不是同一源的相邻两对）。同一个"水平加"在 ps 与 pd 上是两种排布。
   - **Vol. 2A `MOVMSKPS`/`PMOVMSKB`**：把每个元素的**符号位**取出来排成一个 GPR 的位图，不是把元素当数读。
   - **Vol. 2A `MOVLPS`/`MOVHPS` 的 VEX 形式**：三操作数形式取 `SRC1` 的另一半，而**两操作数的 VEX 形式把没写的那一半清零**——`vmovlps xmm1, m64` 与 legacy 的 `movlps xmm1, m64`（保留下半）不是同一条指令。
   - **Vol. 2A `PSRAD` vs `PSRLD`**：算术右移填符号位，计数超过通道宽度时结果是**全符号位**；逻辑右移同样的计数结果是全 0。两者只差一个字母。
   - **Vol. 2A `CVTDQ2PS`/`CVTTPS2DQ`**：`cvt` 按 MXCSR 的舍入模式（默认最近偶数，与 C 的强制转换一致），`cvtt` 向零截断，且 NaN 与越界一律给 **"整数不定值"**（`0x80000000`）——C 的强制转换在同样的输入上是未定义行为，所以这里写成显式比较加常量。
   - **Vol. 2A `BLSI`/`BLSMSK`/`BLSR`**：隔离最低有效位 / 掩到该位为止 / 清掉该位；三个在源为 0 时都有定义（结果是 0），且都按结果置 ZF/SF。
   - **Vol. 2B `TZCNT`/`LZCNT`**：源为 0 时结果是**操作数宽度**，与 `BSF`/`BSR` 的"未定义"不同——这就是它们存在的原因。
   - **Vol. 2A `CMPXCHG`**：ZF 是"目的 == rax"的**相等**，而 CF/PF/AF/SF/OF 来自同一次减法的其余部分；相等时写源，不等时把旧值写回 rax。把它接回标志模型的方式是把它当成一次 `cmp 目的, rax`，因为 `jne` 之后读的就是这一位。
   - **Vol. 2B `XADD`**：目的得和、源得旧值，两个操作数都先读后写；标志按 `add` 的结果置。
   - **Vol. 2A `PSIGNB`/`PSIGNW`/`PSIGND`**：第二个源的每个元素是**符号**——为负则对第一个源取反、为零则清零、为正则原样保留。所以它是一条"按元素查表"的指令，不能写成乘法，也不能只按位运算。
   - **Vol. 2A `VINSERTPS`**：立即数的 `[7:6]` 选源里哪个元素、`[5:4]` 选它落到哪、`[3:0]` 是**最后要清零**的四个通道掩码。三段各管一件事，任何一段读错都是"看起来搬对了但其余通道没清零"。
   - **Vol. 2A `CVTTSS2SI`/`CVTTSD2SI`**：向零截断，且 NaN 与越界给 **"整数不定值"**（`0x80000000`）——和 `CVTTPS2DQ` 同一条规矩，C 的强制转换在这里是未定义行为。
   - **Vol. 2A `SQRTPS`/`SQRTPD`/`SQRTSS`/`SQRTSD`**：**正确舍入**（IEEE 754 要求），所以 `sqrtf`/`sqrt` 就是同一条语义——与下一行的近似指令正相反。上游 `5f51daaa` 把 `SQRTSD` 放进处理器里跑，是同一个判断。
   - **Vol. 2A `MOVSHDUP`/`MOVSLDUP`/`MOVDDUP`**：纯 gather（每个 64 位通道取偶数/奇数/同一个元素复制两遍），所以能走 `weave`；`vmovddup` 还允许源在内存里（`m64`），这时它的"源是寄存器"的前提不成立。
   - **Vol. 2B `PTEST`/`VTESTPS`/`VTESTPD`**：`ZF = ((SRC1 AND SRC2) == 0)`、`CF = ((SRC2 AND NOT SRC1) == 0)`，OF/SF/AF/PF 清零——**与落进 ZF、与非落进 CF**，与名字给人的直觉相反。而 VTESTPS/VTESTPD 只比**符号位**（"bitwise comparison of all the sign bits of the packed elements"），所以按整字的与来算，会在两个同号数上给出相反的答案。§5⑤a 记的就是这两条叠在一起的后果。
   - **Vol. 2B `ROL`/`ROR`**：只写 CF 与 OF，**保留** ZF/SF/PF/AF。所以"旋转夹在比较与分支之间"时，相等与符号位仍然有效，无符号与有符号序关系不再有效——标志模型里为此单独有一个 `cmp_nocf` 状态。
   - **Vol. 2A `TEST`**：ZF/SF/PF 来自 **`SRC1 AND SRC2`**，不是 `SRC1`。写成"第一个操作数非零即真"会把每一条 `test …, imm` 的位测试都做反（§5⑤c）。
   - **Vol. 2B `PAUSE`**、**`INT3`**：前者不改变任何可读状态；后者在 release 构建里只出现在"不返回的调用"之后，是到达即已中止的位置，移植侧落空而不是假装能中断。
   - **Vol. 2A `RSQRTPS`/`RSQRTSS`/`RCPPS`/`RCPSS`**：文档自己写明结果是**近似**（相对误差上界 `1.5×2⁻¹²`），不是 `1/√x` 与 `1/x`。所以 C 里没有任何表达式能复现它——`1/sqrtf(x)` 在最后几位必然不同。唯一忠实的写法是**执行同一条指令**：MSVC 的 `_mm_rsqrt_ps`/`_mm_rcp_ps` 就是它们（SSE 基线，不需要 `/arch`）。这 1,269 个函数是"拒绝"清单里唯一一类**不该**靠算术补齐的。
   - **Vol. 2A `VFMADD132/213/231` 家族**：三个数字是"第一个因子、第二个因子、被加数"分别落在哪个**操作数位置**（`132` = `DEST*SRC3+SRC2`、`213` = `SRC2*DEST+SRC3`、`231` = `SRC2*SRC3+DEST`）。融合只舍入一次，所以 `a*b+c` 与它差一位尾数；`_mm_fmadd_*`/`_mm_fmsub_*`/`_mm_fnmadd_*`/`_mm_fnmsub_*` 是那条指令本身。**标量形式结果的 `127:32` 保留目标原值**——这一条与"VEX 标量都取 `SRC1`"的直觉相反，是硬件判的（§5⑥）。
   - **Vol. 2A `VCMPPS`/`VCMPSS` 的 32 个谓词**：AVX 把立即数从三位扩到五位，多出来的十六个是同样八个关系换 quiet/signaling 配对（只影响异常，不影响掩码），再加 `GE`/`GT`/`FALSE`/`TRUE`。差别只在异常上，所以每个都能折叠到它表示的那个关系上。
   - **Vol. 2A `VROUNDPS`/`VROUNDSS`/`VROUNDPD`/`VROUNDSD`**：`imm[1:0]` 选方向（最近偶数/向下/向上/向零），`imm[3]` 只是抑制精度异常，`imm[2]=1` 时改为读 **MXCSR**——最后这一种本移植**拒绝**，因为 MXCSR 不在模型里，猜它等于猜默认值。其余四个方向与 `_mm_round_*` 的常量一一对应。
   - **Vol. 2A `VPACKSSDW`/`VPACKUSWB` 等**：源一律按**有符号**读，饱和到目标范围——`packuswb` 是把 `int16` 夹到 `[0,255]`，按无符号读会把 `-1` 当成 `65535` 再夹成 `255`（本该是 `0`）。256 位形式在**每个 128 位通道内部**打包，不是把两半拼起来再打。
   - **Vol. 2A `VPSHUFB`**：逐字节查表，掩码字节最高位为 1 则该字节清零，否则取**通道内**第 `(掩码 & 0x0F)` 个字节。
   - **Vol. 2A `VPSHUFD`/`VPSHUFLW`/`VPSHUFHW`/`VPERMILPS`（立即数形式）**：每两位选一个元素；`pshuflw`/`pshufhw` 只动低半或高半，另一半原样保留，而 `vpermilps` 的立即数形式与 `pshufd` 是同一件事（变量形式是另一个操作数，不走这条）。
   - **Vol. 2A `VPEXTRB`/`VPEXTRW`/`VPEXTRD`/`VEXTRACTI128`/`VINSERTI128`**：抽/插单个元素或整个 128 位通道；写进 32 位 GPR 时**零扩展**，`vinserti128` 的另一个通道来自第二个源（VEX 的 NDS 形式）。
   - **Vol. 2A `VCVTPS2PH`/`VCVTPH2PS`**：半精度往返，`cvtps2ph` 的 `imm` 也是四方向 + "读 MXCSR"（后者拒绝）；只写目标的一半字节时**其余清零**。
   - **Vol. 2B `BTS`/`BTR`/`BTC`**：CF 得到的是**改动之前**那一位，其余标志不动——与 `BT` 同一条规矩，所以三者复用同一个 `cf` token。内存目标会跨字节寻址，不在寄存器版本这条规则里。
   - **Vol. 2A `POPCNT`**：数 1 的个数，`ZF` 从结果、`CF`/`OF`/`SF` 一律清零（与 `and` 不同的地方就在 SF）。
   - **Vol. 2B `BZHI`**：索引大于等于宽度时结果**原样不动**、索引为 0 时结果全零，两个边界都在指令里，所以直接用 `_bzhi_u32`/`_bzhi_u64`。**标志**：ZF/SF 是结果的，CF 是"索引 ≥ 宽度"（用索引的低 8 位比），OF 清零，AF/PF 未定义——所以 `bzhi` 之后 `je` 能过、`jp` 不能。
   - **Vol. 2A `MUL`/`IMUL` 单操作数的标志**：CF 与 OF 说的是同一件事——"高半里有没有超出低半的东西"，无符号看高半非零、有符号看高半不是低半的符号扩展；ZF/SF/AF/PF 未定义。这一条决定了 `mul` 之后只允许 `jb`/`ja`/`jo`/`jno`，`jz` 一律拒绝（跳过一个未定义的位就是猜）。
   - **Vol. 2A `PALIGNR`**：把两个源按 `src1:src2` 拼成 32 字节再右移 **imm 个字节**取低 16 字节；256 位形式在**每个 128 位通道内部**各拼各的；`imm > 31` 时结果全零（不是取模）。
   - **Vol. 2A `VPERMILPS` 的变量形式**：控制字**逐元素**给（每格低两位选同通道内的哪一格），与立即数形式"一条控制字管全部"是两条指令，不能共用代码。
   - **Vol. 2A `ADC`/`SBB`**：进位是**第三个加数**（`DEST := DEST + SRC + CF`），`CF` 是这次加法的输出；OF 是两个源与结果的符号位组合。所以 `adc` 不是 `add` 的语法糖——它**读** CF，CF 必须先是一个能写出来的值（`tools/branch.py` 的 `carry_expression`）。
   - **MSVC `_addcarry_u64` / `_subborrow_u64`**：这两个 intrinsic 就是 `ADC`/`SBB` 本身（进位当返回值出得来），所以 64 位的进位链用它们；窄操作数在 64 位里算，进位看第 `bits` 位。
   - **Vol. 2A `SHL`/`SHR`/`SAR`**：**计数为 0 时四个标志一个都不动**（"If the count is 0, the flags are not affected"）——所以"结果决定 ZF"只在立即数非零时成立，`cl` 里的计数只能拒绝。CF 是移出去的最后一位，OF 只在移一位时有意义。
   - **Vol. 2B `SHLD`/`SHRD`**：空出来的位由**源**的高/低位补上；`n = 0` 时结果是目标原值，而 `x >> (bits - 0)` 在 C 里是按位宽取模的移位（未定义行为），不能直接写。
   - **Vol. 2A `TZCNT`/`LZCNT` 的标志**：ZF 与 CF 说的是"**源**是零"，而源为零时**结果**是操作数宽度（32/64）——拿结果当 equality 判断是错的。SF/OF/AF/PF 在 SDM 里未定义，凡是要它们的条件一律拒绝。
   - **Vol. 2A `PABSB`/`PABSW`/`PABSD`**：有符号进、同宽无符号出，`-128` 的绝对值是 `128`（不是饱和到 `127`）。
   - **Vol. 2A `VPMASKMOVD`/`VPMASKMOVQ`/`VMASKMOVPS`/`VMASKMOVPD`**：`IF SRC1[i+31] THEN ... FI`——**每个元素自己的最高位**决定这一格走不走；载入形式把未选中通道**清零**，存储形式**不改内存**。两个方向不对称，所以不能写成"先整块读、再按掩码选"。
   - **Vol. 2A `VPSLLVD`/`VPSRLVD`/`VPSRAVD`**：移位量是**每个元素一个**，过界时**饱和**（逻辑移得 0、算术移得符号位），不是标量移位那种"按位与 31"。
   - **Vol. 2A `PMINSD`/`PMINUD` 等**：符号是**指令**的，`pminsd` 与 `pminud` 只差一个前缀，在 `0x80000000` 那一格分道扬镳。
   - **Vol. 2A `VPERMQ`/`VPERMPD`（立即数）**：两位一个元素、在**整个 256 位**里挑；`VPERMILPD` 改成在**每个 128 位通道内部**挑（一位一个），控制位按通道重复。
   - **Vol. 2A `VCVTPD2PS`/`VCVTPS2PD`/`VCVTDQ2PD`**：只写目标低半时**其余清零**；VEX 的 128 位形式再清 `255:128`（§5⑧ 的第一个坑）。
   - **Vol. 2A `VADDSUBPS`/`VADDSUBPD`**：从 `DEST[31:0] := SRC1 - SRC2` 起头——**偶数通道减、奇数通道加**。名字里的 "addsub" 不是执行顺序，写反是一整条指令的错（§5⑧）。
   - **Vol. 2A `BLSI`**：ZF/SF 从结果来、OF 清零；**CF 的文档说法与实测不一致**——片段差分里源不为零却是 CF=1，说明这一位未定义，所以只承认"溢出清零"。
   - **Vol. 2A `MOVBE`** 与 **`BSWAP`**：`_byteswap_ulong`/`_byteswap_uint64` 就是它们；`bswap` 没有 16 位形式（那个编码未定义）。
   - **Vol. 2A `MFENCE`/`LFENCE`/`SFENCE`/`PREFETCHh`**：架构上不改变任何可读状态（预取连无效地址都不报故障）。移植里是空操作，但**不能拒绝**——一条提示不该废掉整条函数。
   - **Vol. 2A `BT`/`BTS`/`BTR`/`BTC` 的内存形式**：位号**按有符号值**解释，字节地址是 `基地 + (位号 >> 3)`（算术右移），位是 `位号 & 7`——所以负位号落到基地**之前**的那些字节。寄存器形式相反：它在操作数宽度内取模。两种形式的地址规则不同，不能共用一个式子。**立即数形式不跨字节**：位号在宽度内取模、地址停在原处（汇编器把大位号编成位移，那是另一条编码）。
   - **Vol. 2A `PHADDW`/`PHADDD`/`PHSUBW`/`PHSUBD`/`PHADDSW`/`PHSUBSW`**：与 `HADDPS`/`HADDPD` 是**同一条规则换元素宽度**（每个 128 位通道里两两合并，源1 在前、源2 在后）；只有 `*SW` 两条夹到 `int16` 范围，不能用 C 的 `+`。
   - **Vol. 2A `MUL`/`IMUL` 的单操作数形式**：**双倍宽度**的乘积（`AL×r/m8→AX`、`AX×r/m16→DX:AX`、`EAX×r/m32→EDX:EAX`、`RAX×r/m64→RDX:RAX`），与 `imul r, r/m` 那条只留低半的指令不是同一件事。16 位这条**没有** `#DE` 风险（乘积总装得下 32 位），所以 `mul` 能做而 `div` 16 位不能。
   - **Vol. 2A `PSLLDQ`/`PSRLDQ`**：按**字节**在**整个 128 位**里移（不是按元素），计数超过 15 就整个清零而不是取模；VEX 形式的目的寄存器**不是**源，要先搬一格。
   - **Vol. 2A `VPERM2F128`/`VPERM2I128`**：两个源按 128 位拼成四格，低两位挑结果的低半、`imm[5:4]` 挑高半，`imm[3]`/`imm[7]` 各自把那半边清零；两者选择位含义完全相同，只是编码分属浮点与整数。
   - **Vol. 2A `VCVTTPD2DQ`**：截断没有舍入模式可选，因此**不读 MXCSR**——这是它可以从 `vcvtpd2dq` 里单独做出来的原因；越界与 NaN 落到 `INT32_MIN`（integer indefinite），不是 C 强转的未定义行为。
   - **Vol. 2B `RORX`**：循环右移但**不写标志**——这是它与 `ror` 的全部区别，也是它常出现在比较与分支之间的原因。
   - **Vol. 2A `ADD`/`SUB` 的 `CF`/`OF` 定义**：`add` 的 CF 是"结果比任一操作数小"、`sub` 的 CF 是"被减数小于减数"；OF 是两个源与结果的符号组合。**另一个操作数不必在指令前存一份**——`add` 的被加数是 `结果-源`、`sub` 的被减数是 `结果+源`（模 `2^bits`），所以有结果与源就够反推。指令级差分（`add`/`sub` 各 5 例，四个标志全读）把这条反推验成了 500/500。
   - **Vol. 1 §3.4.1.1**：32 位写清零高半——`mov esi, eax` 是清零，不是转换。
5. **Microsoft PE/COFF Specification** — `.pdata` / `RUNTIME_FUNCTION` 布局。
6. **MSVC 内建函数文档** — `_udiv128` / `_div128`（`div`/`idiv` 的 128÷64 就是这条指令本身，所以在除零与商溢出上**与硬件一同 `#DE`**，不需要自己发明边界行为）、`_umul128`（`mulx`，也是 `mul r/m64` 的高半）、`_mul128`（`imul r/m64` 的有符号版本——`mul`/`imul` 单操作数形式的双倍宽度结果用这两个，而不是自己拼两个 32 位乘）、`__readgsqword`（`gs:` 的 TEB 基址）、`_setjmp`/`longjmp`（逐例故障恢复）、`_BitScanForward64`/`_BitScanReverse64`（`tzcnt`/`lzcnt` 的零输入分支，因为返回值的"失败"正是答案）、`_mm_rsqrt_ps`/`_mm_rsqrt_ss`/`_mm_rcp_ps`/`_mm_rcp_ss`（近似指令只能执行它）、`_mm_fmadd_*`/`_mm_fmsub_*`/`_mm_fnmadd_*`/`_mm_fnmsub_*`（融合乘加只舍入一次）、`_mm_round_ps`/`_pd`/`_ss`/`_sd` 与 `_MM_FROUND_*` 四个方向常量、`_mm_cvtps_ph`/`_mm_cvtph_ps`（F16C）、`_mm_move_ss`/`_mm_cvtss_f32`（标量只换低 4 字节的手法）、`_bzhi_u32`/`_bzhi_u64`（`bzhi` 的两个边界就是它）。**`__popcnt` 刻意没用**：没开 `/arch:SSE4.2` 时它退化成一次运行库调用、链接不上，所以 `popcnt` 用的是逐位归并的定长式子。
7. **解析与构建工具**：`capstone`（反汇编）、`pefile`（PE 解析）、`cl.exe`、`rustc`/`llvm-mc`（内联汇编的 VEX 编码）。

`ff06794b`（BMI2 移位）、`9f13c507`（legacy SSE2 浮点搬运）、`3d618698`（`MINSD`/`MAXSD` 的 DAZ）、
`c3221992`/`b291e792`（VEX 打包整数与字节比较）、`4ea0c770`（`VPTEST`/`VTESTPS`/`VTESTPD`——
这一轮实现了，而且**没有照抄它注释里的 CF/ZF 归属**，见 §5⑤a）、`6a127266`（`BLSI`/`BLSMSK`/`BLSR`）、
`5f51daaa`（"run `SQRTSD` on the processor"——和我们的 `sqrt` 走同一条判断：正确舍入的那条浮点平方根
可以直接交给 C，近似的 `rsqrt` 不行）、`780f3c0a`（x87 `F2XM1`/`FYL2X`/`FYL2XP1`，本仓库的 x87 还是空白）。
这两轮把上游从 `a6967446` 推到 `fbe249f6`，共 44 条提交，CPU 侧只有 3 条：

- `bb1addf2`（`VEX.128/256` 水平的与**交替**加减浮点）——`VHADDPS/PD`、`VHSUBPS/PD`、`VADDSUBPS/PD`，

- `780c0bc4`（BMI2 `BZHI`/`MULX`/`PDEP`/`PEXT`，688 行 + 1,898 行测试）——`bzhi`/`mulx` 早就有；
  `pdep`/`pext` 在这个映像的拒绝面里**一次都没出现**（不到 3 个函数），所以只记不写。
- `d371ce46`（16 种 `VEX.256` 跨通道扩展与 dword/qword 解包）——`VEC_EXTEND` 的十二种 `pmovsx*`/`pmovzx*`
  与 `VEC_UNPACK` 上一轮就做完了，**已覆盖**。

其余 41 条是 shader / startup / d3d12 / CI，没有指令语义。上一轮区间 `e4e2b46d..a6967446` 只有
`a6967446`（`exe_aot.py` 的 `os.replace` 原子落盘 + 750 行 CLI 测试），"写完再原子替换"本仓库早就在用
——差分前先写一份 `snippets.exe` 副本、从不改原件（`tools/diff.py` 的 `snippets()`）。

两条**没有**采纳的差异依然成立：

- 上游给 BMI2 那一族配了 1,898 行测试，我们的对应物是"一条指令一个函数"的片段差分（145 条 × 4 例）——
  同样的想法（**每条指令单独可证**），落点不同：他们比的是自己两套实现的输出，我们比的是硬件。
- 上游按指令族拆成多个升举器文件（现在有十几个 `cpu_*_aot.py`），本仓库只有一个 `lift.py` + 一张 `vec_line`。
  `vec_line` 这一轮从 120 行长到 400 行，且开始出现"一族一张表"（`VEC_BLEND`/`VEC_UNPACK`/`VEC_SHIFT`/`VEC_CMP_INT`
  加上这一轮的七张新表）——**这个决定到了该重做的时候**，拆分判据已经摆在眼前：`HADDPS` 与 `HADDPD` 的排布不同、
  `PSRAD` 与 `PSRLD` 的填充不同、`vaddsubps` 与 `vaddps` 只差"偶数通道反向"。一张表能表达的就不该是一个模块
  （`vaddsubps` 属于表），但排布规则不同的应该分开（`haddps`/`haddpd` 属于两个文件）。
