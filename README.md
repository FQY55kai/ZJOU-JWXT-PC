# ZJOU 教务系统 PC 移植

把一台 **x86-64 主机独占大作**搬到 Windows 上原生运行。不走模拟器，不走"运行时翻译二进制"（HLE），走**静态重编译**：离线把主机镜像里的机器码翻成可编译的 C++，再配上我们自己写的运行时与渲染器。

> **本仓库不含任何游戏数据、不含反编译产物。** 只含工具与文档；使用者需自备正版。

---

## 一、为什么重新开一个项目

上一个仓库（运行时翻译路线）已经能跑：能进世界、能操作、画面正常。它的账本是这样的（世界场景稳态，实测）：

| 环节 | 每帧 | 主机上对应 |
|---|---|---|
| 帧总长 | **200.7 ms**（5.0 fps） | 33.3 ms（30 fps） |
| 命令录制 | **149.1 ms**，35,766 次调用，6 线程 | ≈0，硬件直接消费绘制包 |
| GPU 执行 | 103.3 ms | ≈33 ms |
| 主机内存 → 宿主副本 | 45.9 ms / 122.9 MB | 0，统一内存 |
| 宿主副本 → 主机内存 | 40.9 ms / 42.5 MB | 0 |
| 描述符翻译 | 每帧 11,224 张表 | 0，shader 直接按地址读 |

这五项**没有一项是"实现得不够好"**，全是"主机省掉的那一层，我们必须自己做一遍"。两天的调参实测：能拿回 10–20%，拿不回 6 倍。所以换路线。

## 二、这条路能买到什么（以及买不到什么）

先说清楚最容易搞错的地方：**guest 和 host 都是 x86-64，这里没有"翻译红利"**。N64Recomp / XenonRecomp / PS2Recomp 挣的是跨 ISA 的钱（MIPS/PPC 每条指令在 PC 上都要解释一次）；本作 guest ISA 与 host 相同，机器码本来就是原生的。

静态重编译在这里买到的是另外三样：

| 买到 | 为什么值钱 | 对应上面的成本 |
|---|---|---|
| **可编辑的代码** | 现在写死在二进制里的调用序列，变成可改的 C++：可以把 4,544 条绘制合成批量提交 | 命令录制 149 ms |
| **图形边界整体替换** | 不再"翻译主机图形调用"，而是在提交边界写自己的渲染器（bindless + GPU-driven），像 RT64 那样 | 描述符翻译、绘制重放 |
| **不再需要三份内存** | 代码里可以把主机指针改成真实指针，统一内存的模拟随之消失 | 165 MB/帧 往返、87 ms |

买不到的是：**时间**。上游 95 MB 代码、30 万个函数，L1–L3（编译器工程）一个人能做，L4–L5（运行时与渲染器）要团队。**在头 6–12 个月，这条路线一定比现在能跑的 HLE 更差**——这是必须接受的账。

## 三、已经跑通的第一步（不是 PPT）

`tools/probe.py` —— 只读二进制的 `.pdata` 异常表，不要符号表：

```
.text            95.25 MB
函数数           299,257（覆盖 .text 的 92%）
代码量           88.1 MB，中位函数 117 B，24% 小于 64 B，最大 129,632 B
导入             MSVCP140(113) / CRT / libHttpClient(38) / Bink(23) / xmem(12)
图形边界         没有任何 d3d12.dll / dxgi.dll 导入
```

最后一行是关键情报：**图形不走导入表**（静态链进镜像或经系统 vtable），所以"按符号拦图形调用"不可行——必须在重编译之后按代码位置改。这恰好是重编译相对 HLE 的真正优势。

`tools/lift.py` —— 反汇编 → 生成 C → 本机 MSVC 编译 → 运行 → 与独立解释器差分：

```
可升举子集（无调用、无分支）   119 个函数
差分                        119 / 119 一致（0 差异）
```

覆盖率只有 0.04%，它的意义是**链路通了**：`.pdata` → Capstone → C → cl.exe → 执行 → 比对，全是真实产物。

`tools/oracle/`（Rust）—— **硬件差分**：same ISA ⇒ 原始实现不需要模拟器，把函数字节拷进可执行页、设好 16 个寄存器、`call` 过去、读回来：

```
oracle 自检（mov rax,rcx; add rax,rdx; ret）   rax = 42 ✓
真实函数 vs 生成的 C                            40 / 40 一致
```

这比"两份自己的实现一致"强一个档：裁判是硬件。写这套桩踩到的三个坑，都写进了代码注释——

1. **不能声明 `nostack`**：块里改了 `rsp`，编译器却会按"栈没动"优化，用完的栈槽被 guest 覆盖。
2. **`rbx`/`rbp` 无法声明为 clobber**（LLVM 保留），必须自己在块内保存恢复；其余 14 个用 `clobber_abi("win64")` + 显式 `out`。
3. **RVA 不是文件偏移**：第一版直接按 RVA 从文件里拷字节，跑的是垃圾指令，全部访问违例。要过一遍段表。

还有一个**结构性发现**：`.pdata` 里有相当一部分条目不是函数，而是函数的片段（冷块、funclet），它们的 `ret` 读的是父函数压进去的返回地址。判据可以静态算出——**入口与出口的 `rsp` 位移必须为 0**。这条判据现在是 `tools/diff.py::balanced()`，也是将来正式 lifter 必须带上的。

### 覆盖率到底卡在哪（20,001 个函数采样）

| 原因 | 数量 | 占比 | 意味着 |
|---|---|---|---|
| 以尾调用 `jmp` 结尾 | 12,130 | **61%** | 薄壳与导入桩，**支持"调用"就拿下** |
| 有分支 | 7,794 | **39%** | 需要 CFG 重建 + 标志位模型 |
| SSE/AVX | 60+ | 0.3% | 向量指令族，逐个补 |
| RIP 相对寻址 | 2 | — | 需要镜像基址 + `.reloc` |

**99% 卡在两件事：调用、分支+标志。** 这就是前两层的全部内容。

## 四、实现办法

### 总体结构

```
主机镜像 (.exe/.dll)
   │  probe        读 .pdata 拿函数边界（92% 覆盖）
   ▼
函数表 ──► lifter ──► 每个函数一份 C++（带 CFG、标志位、间接调用表）
   │                        │
   │  差分 oracle ◄─────────┘   同 ISA ⇒ 在本进程里直接 call 原始字节对比
   ▼
recompiled.exe  +  runtime（系统调用层）  +  renderer（图形层）
```

### 五层

| 层 | 内容 | 解锁 | 估时（1 人 + AI 辅助） |
|---|---|---|---|
| **L1** | 尾调用/直接调用、导入桩、RIP 相对 + `.reloc`、子寄存器（eax/ax/al） | 61% 的薄壳 + 大量小函数 | 2–4 周 |
| **L2** | 分支 → 标签 + `goto`、完整标志位（CF/OF/SF/ZF/AF/PF）、`setcc`/`cmovcc` | 再 39% | 3–6 周 |
| **L3** | 硬件差分 oracle（见下） | 正确性可自动化 | 1–2 周，与 L2 并行 |
| **L4** | 运行时层：系统 API 的静态实现 | 能启动 | 2–3 个月 |
| **L5** | 渲染器：提交边界替换，bindless + GPU-driven | **超过 30 fps** | 6 个月+ |

### 三个决定成败的设计选择

1. **不重建 ABI，只重建语义。** 重编译后的函数仍是 `rdi/rsi/rdx/rcx` 那套寄存器约定、仍读写同一块"guest 内存"。这样任何一处未重编译的函数都能回落到原始机器码（同 ISA，直接 `call`），项目可以从第一天就跑起来，而不是等到 100% 才第一次运行。
2. **差分 oracle 是免费的。** guest 与 host 同 ISA，所以"原始实现"不需要模拟器：把函数字节拷到可执行内存，与重编译版本用同一组随机输入各跑一遍，比较寄存器与内存。前作（N64/PSP）要拿整个模拟器当裁判，我们只需要 5 行汇编桩。
3. **图形在提交边界切，不在 API 边界切。** 目标不是"把主机的 D3D12 调用翻译成 PC 的 D3D12 调用"，而是"把这一帧要画什么接过来自己画"。前者注定慢，后者才有机会超过主机。

## 五、设备

| 用途 | 配置 | 说明 |
|---|---|---|
| 开发/基准机（现有） | i9-13900HX + RTX 4080 Laptop 16 GB + 32 GB DDR5 | 现有实测环境；重编译本身是 CPU/IO 密集，这台够用 |
| 重编译服务器（可选） | 任意 16 核以上 + 64 GB | 30 万函数的全量重编译 + 每晚差分回归，本地跑一次约数小时 |
| 目标最低配置 | x86-64 v3（AVX2）+ 8 GB 显存 + 16 GB 内存 + SSD | 与主机同代（RDNA2 / Ampere 之后）的卡即可 |
| 目标推荐配置 | 12 GB 显存以上 | L5 的 GPU-driven 提交吃显存换 CPU |
| 为什么不用 NVIDIA 特性 | — | 主机是 AMD RDNA2：wave64、无 bindless 堆限制。用通用 D3D12 特性集，不绑厂商 |

> 注：上一轮实测发现 NVIDIA 在 D3D12 下 `wave lanes = 32`，模拟主机 64 车道波要拆两波 + LDS 交换，指令数最多翻倍。这是 L5 之前必然背着的税；L5 换渲染器后可以用 compute 重写热点，绕开大部分。

## 六、收益

| 谁 | 收益 |
|---|---|
| 玩家 | 原生 Windows 运行，不需要主机、不需要模拟器；目标 60 fps（现路线 5 fps） |
| 项目 | 从"追着二进制打补丁"变成"有源码级代码"，可维护、可优化、可被别人接手 |
| 社区 | 一套 **x86-64 主机 PE 的静态重编译工具链**——这类工具此前只存在于非 x86 主机（N64/GC/Wii/PS2/PS3/X360），这是第一份 |
| 学术/工程 | 大规模二进制翻译 + 差分测试的完整案例：30 万函数、可量化的覆盖率与正确率 |

## 七、要拉的人

| 角色 | 负责 | 为什么专职 |
|---|---|---|
| 二进制翻译 / 编译器 | L1–L3：CFG 重建、标志位正确性、差分框架 | 正确性靠大规模差分迭代，不能兼职 |
| 图形 / 渲染器 | L5：帧图、bindless 描述符、GPU-driven 提交 | 决定最终能否超过 30 fps |
| 系统层 | L4：系统 API 的静态实现 | 工作量可控，但接口面很宽 |
| 测试 / 自动化 | 每晚全量重编译 + 差分 + 冒烟 | 没有它，改一处没人知道坏没坏 |

## 八、法务边界
