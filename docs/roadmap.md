# 路线图

> **2026-11-26 停在这里，从这里接着做**：`tools/` 下已有 probe / lift / branch / diff / callgraph / functable / cover。
> oracle 可跑；子寄存器、`movabs`、`[rip+d]`、ALU/BT 标志、CFG + 跳转表已通，
> 分支通道接受 **14,330 / 40,001（35.8%）**。
>
> **但验证撞到了天花板**：内存模型还是 `stk + (addr & 255)`，只有 2.5% 的函数能进差分，
> 8,001 个用 rip 的函数里 0 个能进。所以**下一件事是 M1.2（真实地址空间）**，不是继续加指令覆盖——
> 否则接受量再涨也只是"翻译了、没人裁判"。

每个 milestone 的验收标准都写在下面。**没有验收标准的工作不算完成。**

## M0 —— 链路打通（已完成）

- [x] `.pdata` 取函数表：299,257 个函数，覆盖 `.text` 92%
- [x] 导入面清点：136 + 130 个 CRT 符号、38 个 HTTP、23 个视频、12 个内存
- [x] 确认图形无导入（静态链），确定"按代码位置改"的策略
- [x] 直行子集升举 + 差分：119 个函数，119/119 一致
- [x] **硬件差分 oracle（Rust）**：自检通过，真实函数 40/40 与原始机器码一致
- [x] 片段识别：`.pdata` 里的冷块/funclet，判据 = 入口与出口 `rsp` 位移为 0

**验收**：`python tools/lift.py` 能生成 C、编译、运行、报告一致率。✅

## M1 —— 调用与寻址（2–4 周）

- [ ] 尾调用 `jmp` → `return f(args)`
- [ ] 直接 `call rel32` → 函数表查表
- [ ] 导入桩识别（`jmp [rip+iat]`）→ 直接绑运行时桩
- [x] RIP 相对寻址 + 映像映射（`[rip+d]` → `img + rva`；`image_loader()` 按段表建映像）
- [x] 绝对地址立即数随映像重定位（`imm64` 落在映像范围内）
- [x] 子寄存器语义（`eax/ax/al/ah`、`r8d/r8w/r8b`：32 位写清零高半、8/16 位保位）
- [x] `movabs`（`mov r64, imm64`，580 个函数卡在这）
- [ ] 降级路径：不认识 → `ORIGINAL` + 运行时 `call` 原始字节
- [ ] `segment` 前缀（1,004 个函数，多为 `gs:` TEB/TLS 访问）

**验收**：可升举函数比例 ≥ 60%；这批函数的差分通过率 ≥ 99.9%；未通过的必须能说出原因。

## M1.2 —— 真实地址空间（阻塞项，优先于一切）

现在的内存模型是 `stk + (addr & 255)`：把所有内存都当作那个 256 字节栈。真实函数第一句就是
`mov [rcx], rax`，写的是调用方给的缓冲区，于是被 `safe()` 整个滤掉——**只有 2.5% 的函数能进差分**。

- [ ] `lift.py`：内存操作数直接 `*(uintN_t *)(uintptr_t)addr`，去掉 `stk` 与 `& 255`；`push`/`pop` 变真内存写；签名 `(r, stk)` → `(r)`
- [ ] `oracle`：栈与 arena 都 `VirtualAlloc` 在固定地址，两侧同址
- [ ] 差分比 arena 哈希，而不只是 16 个寄存器 + 256 字节栈
- [ ] `xmm0-15` 进比较（现在完全没碰向量寄存器）

**验收**：`--limit 400` 里"能跑"的比例从 2.5% 提到 ≥ 60%；构造函数/setter 类函数有通过率数字。

## M1.5 —— 闭包升举（新，优先于 M2）

- [x] 调用图：`call rel32` → 目标 RVA；尾调用 `jmp` 同表（`tools/callgraph.py`）
- [x] 函数表生长：`call` 目标即函数起点，迭代到收敛（`tools/functable.py`，+16,733 个起点）
- [ ] 逆拓扑序升举一整份 C，`call` 变直接调用
- [ ] `call_original(rva)` 兜住未覆盖目标（复用 oracle 的调用桩）
- [ ] 差分改为"链接整份代码后跑入口"，不再单函数独立跑

**为什么插在前面**：分支升举器只接受 121 / 207,811，墙是"调用"不是"分支"。单函数独立成立这条路本身就走不通。

## M2 —— 分支与标志（3–6 周）

- [x] 基本块 + CFG + 标签/`goto`（`tools/branch.py`，cmp/test + jcc 窥孔）
- [x] 比较数在 `cmp` 处快照（`cmp` 后夹 `mov` 再 `jcc` 时不能读被改写的寄存器）
- [x] `setcc`/`cmovcc` 作为消费者（窄目标也写对宽度）
- [ ] 标志位按"生产者→消费者、无入边直线段"建模（照 X2W 的规则，见 `docs/reference-xbox2windows.md`）
- [ ] `setcc`/`cmovcc` 作为消费者；8/16 位窄算术的 OF/PF 按操作数宽度判
- [x] 跳转表两种模式 → `switch`（`B` 同址、索引可证）：`walk()` 只顺边遍历，表字节不再被当代码解码
- [ ] 条件跳转映射
- [ ] 标志位活跃性分析（只算被读的）
- [ ] `setcc` / `cmovcc` / `adc` / `sbb` / 多精度运算
- [x] `jmp` 表（间接跳转）：按边遍历 + 跳转表 → `switch`（前 4 万函数：13,882 → 14,330）
- [ ] 间接跳转里剩下的 584 个：虚表尾调用、导入 thunk（不是跳转表，需要运行时派发表）

**验收**：可升举比例 ≥ 95%；差分通过率 ≥ 99.9%；条件分支要专门造一个"两路都走"的测试生成器（镜像分支，强制两块都执行）。

## M3 —— 差分基础设施（1–2 周，与 M2 并行）

- [x] Rust asm 桩：调原始字节，导出 16 个通用寄存器 + 内存（`tools/oracle`）
- [ ] xmm0-15 与内存哈希（目前只比通用寄存器与 256 字节栈）
- [ ] 轨迹采样：从真实运行中抓函数入口快照（首版可用 HLE 运行器采）
- [ ] 每日全量回归：30 万函数 × N 组输入，输出通过率与回归列表
- [ ] 失败最小化：给出触发差异的最小输入

**验收**：`cargo test --release oracle` 能在 CI 跑完整表；任何一个函数的通过→不通过都会 fail。

## M4 —— 能启动（2–3 个月）

- [ ] 运行时层：CRT 转发、Win32 转发、xmem 实现
- [ ] 文件层：镜像读取（压缩容器）、异步读取
- [ ] 线程/TLS/异常：跑通初始化
- [ ] 首个可达目标：**进到主菜单**（图形仍走旧的翻译层，先求能跑）

**验收**：重编译版能进主菜单并保持 10 分钟不崩；崩溃必须带函数 RVA。

## M5 —— 超过主机（6 个月+）

- [ ] 图形提交边界替换：绘制压进 POD 数组
- [ ] 描述符整块上传 + `SM6.6` heap 直接索引
- [ ] GPU-driven：compute 剔除 + `ExecuteIndirect`
- [ ] 基准：同场景同视角，与 HLE 版（5 fps / 200.7 ms）逐项对比

**验收**：世界场景 ≥ 30 fps（主机目标帧率），CPU 录制 < 10 ms/帧。

## 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 间接调用无法静态解析 | 覆盖率卡在 70–80% | 运行时查表回退（性能损失可接受）；热点函数手工 devirtualize |
| 异常处理 | 部分模块无法重编译 | 第一阶段整体回退原始字节；第二阶段转 SEH |
| 图形层完全不可切 | 退回"翻译 D3D12"，收益归零 | M4 之前就要做一次"提交点识别"预研，确认边界存在 |
| 人力不足 | 停滞在 M2 | M1–M3 是一个人能做完的，先做到那里再谈 L4/L5 |
| 法务 | 项目被下架 | 不含数据、不含产物、工具定位同前作 |
