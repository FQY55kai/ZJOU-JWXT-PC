# 路线图

每个 milestone 的验收标准都写在下面。**没有验收标准的工作不算完成。**

## M0 —— 链路打通（已完成）

- [x] `.pdata` 取函数表：299,257 个函数，覆盖 `.text` 92%
- [x] 导入面清点：136 + 130 个 CRT 符号、38 个 HTTP、23 个视频、12 个内存
- [x] 确认图形无导入（静态链），确定"按代码位置改"的策略
- [x] 直行子集升举 + 差分：119 个函数，119/119 一致

**验收**：`python tools/lift.py` 能生成 C、编译、运行、报告一致率。✅

## M1 —— 调用与寻址（2–4 周）

- [ ] 尾调用 `jmp` → `return f(args)`
- [ ] 直接 `call rel32` → 函数表查表
- [ ] 导入桩识别（`jmp [rip+iat]`）→ 直接绑运行时桩
- [ ] RIP 相对寻址 + `.reloc`（基址可固定）
- [ ] 子寄存器语义（`eax/ax/al` 掩码与清零）
- [ ] 降级路径：不认识 → `ORIGINAL` + 运行时 `call` 原始字节

**验收**：可升举函数比例 ≥ 60%；这批函数的差分通过率 ≥ 99.9%；未通过的必须能说出原因。

## M2 —— 分支与标志（3–6 周）

- [ ] 基本块 + CFG + 标签/`goto`
- [ ] 条件跳转映射
- [ ] 标志位活跃性分析（只算被读的）
- [ ] `setcc` / `cmovcc` / `adc` / `sbb` / 多精度运算
- [ ] `jmp` 表（间接跳转）：数据流求值域，求不出则降级

**验收**：可升举比例 ≥ 95%；差分通过率 ≥ 99.9%；条件分支要专门造一个"两路都走"的测试生成器（镜像分支，强制两块都执行）。

## M3 —— 差分基础设施（1–2 周，与 M2 并行）

- [ ] Rust asm 桩：调原始字节，导出 16 个通用寄存器 + 16 个 xmm + 内存哈希
- [ ] 轨迹采样：从真实运行中抓函数入口快照（首版可用 HLE 运行器采）
- [ ] 每日全量回归：30 万函数 × N 组输入，输出通过率与回归列表
- [ ] 失败最小化：给出触发差异的最小输入

**验收**：`cargo test --release oracle` 能在 CI 跑完整表；任何一个函数的通过→不通过都会 fail。

## M4 —— 能启动（2–3 个月）

- [ ] 运行时层：CRT 转发、Win32 转发、xmem 实现
- [ ] 文件层：镜像读取（压缩容器）、异步读取
- [ ] 线程/TLS/异常：跑通初始化
- [ ] 首个可达目标：**进到主菜单**（图形仍走旧的翻译层，先求能跑）

**验收**：重编译版能进主菜单并保持 10 分钟不崩；崩溃必须带函数 RVA。

## M5 —— 超过主机（6 个月+）

- [ ] 图形提交边界替换：绘制压进 POD 数组
- [ ] 描述符整块上传 + `SM6.6` heap 直接索引
- [ ] GPU-driven：compute 剔除 + `ExecuteIndirect`
- [ ] 基准：同场景同视角，与 HLE 版（5 fps / 200.7 ms）逐项对比

**验收**：世界场景 ≥ 30 fps（主机目标帧率），CPU 录制 < 10 ms/帧。

## 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 间接调用无法静态解析 | 覆盖率卡在 70–80% | 运行时查表回退（性能损失可接受）；热点函数手工 devirtualize |
| 异常处理 | 部分模块无法重编译 | 第一阶段整体回退原始字节；第二阶段转 SEH |
| 图形层完全不可切 | 退回"翻译 D3D12"，收益归零 | M4 之前就要做一次"提交点识别"预研，确认边界存在 |
| 人力不足 | 停滞在 M2 | M1–M3 是一个人能做完的，先做到那里再谈 L4/L5 |
| 法务 | 项目被下架 | 不含数据、不含产物、工具定位同前作 |
