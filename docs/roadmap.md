## M1.2 —— 真实地址空间（已完成）

原来的内存模型是 `stk + (addr & 255)`：把所有内存都当作那个 256 字节栈。真实函数第一句就是
`mov [rcx], rax`，写的是调用方给的缓冲区，于是被 `safe()` 整个滤掉——只有 2.5% 的函数能进差分。

- [x] `lift.py`：内存操作数直接 `*(uintN_t *)(uintptr_t)addr`，去掉 `stk` 与 `& 255`；`push`/`pop` 变真内存写；签名 `(r, stk)` → `(r)`
- [x] `oracle`：映像映射在首选基址、arena `VirtualAlloc` 在固定 0x20_0000_0000，两侧同址
- [x] 差分比**整个 arena（16 KiB）**，而不只是 16 个寄存器 + 256 字节栈
- [x] 解释器改成两段式地址空间（`Space`：映像 + arena），随发射器一起被验证
- [x] 桥：`guest_bridge` 让升举代码调用尚未升举的函数，否则只有 0.5% 的函数可测
- [x] `xmm0-15` 进比较（256 位 × 16 个向量寄存器，两侧由记录传入传出）

### 这一版修掉的六个错
每一个都值 8 字节或者一次 SIGSEGV，而且都不会自己暴露：

| 现象 | 原因 |
|---|---|
| 差分永远差 8 字节 | `call` 会把返回地址压进栈，裁判侧没有预充这 8 字节，于是 guest 看到的 `rsp` 整体偏一格 |
| 桥接调用整帧偏移 | 桥自己也要 `call`，预充值必须与"从裁判进入"时不同（8 / 0） |
| 升举过的调用不留返回地址 | 硬件 `call` 会在 `rsp-8` 写一个映像地址；升举成 C 调用后什么都不写，内存比不过 |
| 尾调用整帧偏移 8 | `jmp` 不压栈，但桥按 `call` 补偿了 8 |
| 桥一跳进映像就崩 | 映像被映射成 `PAGE_READWRITE`，代码页不可执行 |
| `ERROR_INVALID_ADDRESS`(487) | 生成的 `lifted.exe` 默认基址也是 `0x1_4000_0000`，把映像的首选基址占了 |

**验收**：`--limit 120` 里"能跑"的比例 **66%（79/120）**，目标 ≥60% 达成；其中 35 个（44%）能和硬件逐字节对上，其余是因为函数读了从未初始化的全局而两侧同时崩溃。

## 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 间接调用无法静态解析 | 覆盖率卡在 70–80% | 运行时查表回退（性能损失可接受）；热点函数手工 devirtualize |
| 异常处理 | 部分模块无法重编译 | 第一阶段整体回退原始字节；第二阶段转 SEH |
| 图形层完全不可切 | 退回"翻译 D3D12"，收益归零 | M4 之前就要做一次"提交点识别"预研，确认边界存在 |
| 人力不足 | 停滞在 M2 | M1–M3 是一个人能做完的，先做到那里再谈 L4/L5 |
| 法务 | 项目被下架 | 不含数据、不含产物、工具定位同前作 |
